## 2. Threat model y trust boundaries

Activos: ejecucion de comandos en el host (sc._ejecutar_comando, Orquestador,
flujo_principal, _ejecutar_planificador); lectura/escritura del filesystem y,
por traversal, de todo el host (~/.ssh, /etc, ~/.snapcontext/config.json con
api_key y tokens); secretos en proceso; integridad del orquestador LLM
(prompt injection via consulta/tema/contenido/updates/eventos); disponibilidad
(daemon, hilos WS, tareas API, difusor interactivo).

Atacantes: usuario local legitimo; proceso local malicioso / otro usuario del
host (alcanza localhost sin auth); vecino LAN (solo si bind no-loopback);
atacante Internet (solo si exposicion + NAT/proxy); falsificador de webhooks
(POST a /webhook/* sin secreto/firma); apps legitimas GitHub/Telegram/Discord
(autenticables solo con secreto/clave); navegador victima (CSRF, query en
historial).

### A. Localhost

Cliente en la misma maquina; bind actual (arrancar_servidor fijo 127.0.0.1;
arrancar_api default 127.0.0.1) hace de localhost el caso por defecto.
Friccion razonable: UI estatica local sin login, PERO capacidades sensibles
(orquestador, run, filesystem write, daemon, tasks) siguen exigiendo API key:
en host multi-usuario / con malware / navegador explotable, "localhost =
trusted" es falso, y el coste de la key en localhost es minimo.
Sensible incluso en localhost: ejecucion de comandos, escritura, cambio de
directorio fuera del proyecto, daemon, plugin_install/remove (codigo de
terceros), /ws/interactive (inyecta al hub ReAct).

### B. LAN

Boundary distinta de localhost. LAN != trusted: movil/IoT/invitado alcanzan el
puerto si el operador abre --api-host. Requiere: (1) auth efectiva sin
fail-open, (2) autorizacion por capacidad (secc. 5), (3) politica remota de
comandos (secc. 6), (4) filesystem boundary central (secc. 7).

### C. Internet / redes no confiables

Pre-requisitos antes de exponer: bind explicito + API key obligatoria + TLS
terminado fuera del gateway (uvicorn actual es HTTP plano) + TrustedHost +
rate limiting + size limits + politica remota + logs sin secretos. Sin TLS la
key viaja en claro: exposicion directa en HTTP plano PROHIBIDA en el M1. Via
soportada: reverse-proxy (TLS + auth) delante del gateway en loopback.

### D. Webhooks (boundary por proveedor, no unificada)

GitHub: HMAC SHA-256 (X-Hub-Signature-256, fallback SHA-1) via
validar_firma contra GITHUB_WEBHOOK_SECRET. Autenticidad real si hay secreto.
Telegram: SIN firma del emisor; webhook_telegram solo verifica que el receptor
tenga TELEGRAM_BOT_TOKEN (503 si falta). Cualquiera con la URL inyecta Updates
falsos al pipeline. Es el webhook mas debil: confianza por URL secreta.
Discord: firma Ed25519 (X-Signature-Ed25519 + Timestamp) via verify_signature
contra DISCORD_PUBLIC_KEY (503 sin clave, 401 firma mala). Correcta.

## 3. Network binding contract

- Bind por defecto: 127.0.0.1 (loopback). arrancar_servidor fijo en loopback;
  arrancar_api default 127.0.0.1. Sin flag explicito nunca otra interfaz.
- Puertos convencionales: web 8000, API 8001 (convencion, no seguridad).
- Escucha no-loopback solo con configuracion explicita (--api-host 0.0.0.0/IP)
  + log de arranque que avise EXPOSING NON-LOOPBACK + negativa a arrancar si
  falta la proteccion requerida.
- Proteccion previa a no-loopback: (1) API key no vacia con entropia minima;
  (2) enforcement central activo (invariante E); (3) politica remota de
  comandos; (4) filesystem boundary. Si falta una, rehusar arrancar.
- Rechazar configuraciones inseguras con error legible (no warning): host
  no-loopback sin API key; 0.0.0.0 sin TLS/proxy declarado; webhook GitHub
  alcanzable fuera de loopback sin secreto (deshabilitar esa ruta).
- No confiar en Host/X-Forwarded-For hasta tener TrustedHost + proxies
  confiables (TrustedHost basico en M1).
- Current: arrancar_api acepta cualquier host sin validacion; sin TrustedHost
  /CORS/rate-limit (test_sin_cors_ni_trustedhost).

## 4. Authentication contract

### 4.1 HTTP

- Autenticados (objetivo): POST /api/v1/query|plan|chat|daemon, GET
  /api/v1/skills|tasks/{id}, via Depends(_autorizar) centralizado.
- Publicos: GET /health y /api/v1/health (solo estado/servicio/version);
  GET / sirve la UI pero NO concede capacidades; /docs|/redoc|/openapi.json
  publicos solo en loopback, deshabilitados o autenticados fuera de loopback.
- Sin API key: PROHIBIDO "todo queda abierto". Objetivo: loopback -> generar
  + persistir clave (comportamiento actual de _clave_api_efectiva) y exigirla;
  no-loopback -> rehusar arrancar. No loguear la clave por request; rotacion
  documentada.
- Credenciales: header X-API-Key primario; query ?api_key= solo compat WS,
  DEPRECATED (queda en historial/logs proxy). Comparacion hmac.compare_digest
  (extender a HTTP; hoy !=). 401 generico + WWW-Authenticate, sin oraculo, con
  rate-limit.
- Current: _autorizar fail-open sin clave (test_api_sin_token_queda_abierta);
  health, /, /docs, webhooks fuera de auth (test_endpoints_publicos_sin_auth).

### 4.2 WebSocket

- Auth ANTES de accept() (orden actual correcto como intencion); credencial:
  ?api_key= o header X-API-Key, misma key que HTTP. Sin lectura de mensajes ni
  hilos ni fijar_evento_callback antes de autenticar. Fallo -> close(1008).
- /ws exige la key de /api/v1/*. /ws/interactive hoy SIN auth (accept
  inmediato, web/app.py ~387-395): objetivo misma auth + capacidad
  interactive.control; en M1 solo loopback, fuera de loopback deshabilitado.
- Ausencia == invalidez -> close(1008) sin distinguir; error en resolucion de
  clave -> rechazar, no abrir.
- Current H1a: _autorizar_ws referencia _API_TOKEN inexistente (el parametro
  real es api_token, la closure es _clave_api; web/app.py:807). NameError ->
  except -> close(1008) siempre: TODA conexion /ws se cierra aun con credencial
  valida. Intencion correcta, implementacion disfuncional. NO corregir en B9.58.

### Principio obligatorio

> Si no hay API key configurada, el gateway NO queda abierto. En loopback la
> genera y la exige; fuera de loopback rehusa arrancar. Cualquier excepcion
> requiere decision explicita por trust boundary; nunca es el default.

## 5. Authorization contract

Authentication (quien) != Authorization (que puede hacer). Estar autenticado
NO concede todas las capacidades del orquestador.

Capacidades minimas: run (RCE directo: WS accion==run, futuro POST /api/v1/run);
task (orquestador general: WS tipo==tarea, POST query|plan, fix|review|plan —
RCE indirecto: ejecuta comandos, edita archivos, --test-loop + --comando-test
fijan comandos); search/explorar (embeddings, rg/grep, grafo: lectura
arbitraria via directorio/tema, DoS); asesor (_asesor_analizar: lectura
masiva); plugins (listar vs plugin_install/remove: instalar = codigo de
terceros, maximo privilegio); filesystem.read (leer_archivo, semantica,
explorar: exfiltracion ~/.ssh /etc config.json); filesystem.write
(guardar_archivo: sobrescritura, persistencia); daemon.manage
(iniciar/detener/intervalo_horas: persistencia periodica); chat
(proveedor/modelo/historial arbitrarios: coste/SSRF); external-effect (red,
PRs, tests).

Reglas: cada mensaje/request se mapea a UNA capacidad antes de ejecutar; sin
mapeo -> denegar. run exige autorizacion de ejecucion remota (secc. 6).
tarea/fix/review/plan pasan por la misma politica que run (cierra H1b).
plugin_install/remove exigen capacidad separada de alto privilegio, denegada
por defecto fuera de loopback. directorio/ruta/archivo/origen/consulta/tema/
comando_test/carpetas son datos no confiables aunque el cliente este
autenticado.

Current H1b: solo run invoca _ws_clasificar_run (clasificar_comando, rechaza
no-directo sin sandbox silencioso: correcto como mecanismo). tarea
(Orquestador.ejecutar_flujo con _construir_args: directorio, test_loop,
comando_test, carpetas), fix/review/plan (flujo_principal,
_ejecutar_planificador), search/explorar/asesor/plugins, leer_archivo,
dependencias, semantica NO pasan por clasificacion equivalente.

## 6. Remote command execution

Mecanismo C2 reutilizable: clasificar_comando -> (directo|sandbox, motivo).
directo solo si: sin metacaracteres amplios (| & ; < > ` $ ( ) newline
backslash, _METACARACTERES_AMPLIOS) + shlex.split valido + binario base en
ALLOWLIST_BINARIOS_DEFECTO (ls cat head tail wc stat file diff tree grep rg
git pytest ruff mypy black isort npm pip pip3 echo which date) + no en
_BINARIOS_SIEMPRE_SANDBOX (eval exec source dd shred truncate base64 xargs
chmod chown curl wget find rm mkswap wipefs fdisk parted, mkfs*) + sin match
blocklist legacy. Allowlist configurable (config.json sandbox_allowlist_
binarios, reemplazo total). Interpretes (python node sh bash), curl/wget,
rm/find/chmod fuera de directo por diseno.

Local vs remoto: en CLI sandbox = ejecutar en Docker o pedir confirmacion (hay
humano y contenedor). En red no hay humano (auto=True, no_confirmar=True) ni
Docker garantizado: redirigir a sandbox en silencio = ejecucion remota opaca;

## 7. Filesystem security contract

directorio = filesystem boundary declarado por request (proyecto raiz que debe
contener la operacion). Default "." (cwd del servidor) solo valido en
loopback; fuera de loopback raiz explicita del operador, nunca cwd implicito.
directorio es input atacante: absoluto, .., symlink, /, /etc, ~/.ssh,
~/.snapcontext. Amenazas: absolutas, a/../../etc/passwd, symlinks (archivo o
padre), TOCTOU (validar -> sustituir por symlink -> escribir), lectura de
sensibles, escritura/creacion fuera, eliminacion futura (hoy sin delete: el
contrato prohibe delete/rename/chmod sin capacidad dedicada; fuera del M1).

PRINCIPIO UNICO: ninguna operacion Web puede escapar de su filesystem boundary
por un camino alternativo al mecanismo central. Todo acceso remoto pasa por un
enforcement point: _resolver_camino() -> _validar_ruta_segura() ->
escribir_archivo_seguro() (lectura: resolver+validar+O_NOFOLLOW; escritura: la
cadena H3 completa). Los handlers no validan por su cuenta.

Primitivas: _resolver_camino (absoluta resuelta + _validar_ruta_segura,
ValueError si escapa; resolucion correcta, insuficiente sola para escritura);
_validar_ruta_segura (resolve + relative_to); escribir_archivo_seguro (unica
via de escritura remota: rechaza absolutas y .. sintactico, normaliza,
revalida, _verificar_padre_seguro, mkdir seguro, O_NOFOLLOW|O_EXCL|O_CREAT;
RutaInseguraError -> error controlado).

Reglas: leer/guardar/dependencias (_grafo_dependencias)/semantica
(_buscar_semanticamente)/explorar (_buscar_en_codigo)/tarea/fix/review/plan/
asesor/plugins/query/plan/chat con directorio -> TODOS por el punto central;
prohibido consumir directorio crudo (estado actual de _dependencias_web,
_semantica_web, _explorar_web, _ejecutar_tarea, _ejecutar_accion,
_ejecutar_tarea_api). Sensibles (~/.ssh, /etc, ~/.snapcontext, .env) denegados
por defecto; sensitive-read granular fuera del M1.

Current H2/H3: H3 (guardar -> resolver -> escribir_archivo_seguro) correcta,
referencia a generalizar. H2: _leer_archivo_web resuelve pero sin O_NOFOLLOW
atomico; el resto consume directorio crudo.

## 8. WebSocket security model

Ciclo normativo:
connection request -> authentication (pre-accept secc. 4.2; fallo close 1008
sin accept) -> accept -> message validation (JSON, tipo/accion conocidos,
tipos y tamanos; fallo -> error tipado, conexion ABIERTA salvo abuso) ->
authorization (capacidad secc. 5; fallo -> error sin ejecucion) ->
operation-specific policy (run secc. 6; filesystem secc. 7; plugins privilegio
alto; interactive abajo) -> execution (hilo+cola, timeouts) -> response (sin
tracebacks ni rutas absolutas). Todo en dispatcher central, no por handler.

Uniformidad (cierra H1b): prohibido que solo run clasifique y el resto llame
al orquestador directo. Cierres: 1008 policy violation, 1009 message too big,
1011 internal error. Mensaje malformado -> log:error + continuar (actual OK);
tipo desconocido -> accion_ejecutada{ok:false} explicito (no continue
silencioso actual). Accion no autorizada -> error + contador; tras N
violaciones close(1008). Violacion de auth nunca llega a accept; violacion
repetida de autorizacion cierra; evento aislado no cierra. Limites: tamano por
mensaje/campo (contenido ya trunca a 400_000 en interactive; extender a /ws +
consulta/comando/tema), rate-limit por conexion, timeout generalizado (run hoy
180s), pool de hilos con tope.

/ws/interactive (maximo privilegio: inyecta diff_respuesta al hub ReAct,
recibe timeline): misma auth que /ws + capacidad interactive.control + solo
loopback en M1 + mismo ciclo (hoy: sin auth, sin validacion de tipo, accept
inmediato).

## 9. Webhook security

Invariante: todo webhook tiene frontera de autenticidad explicita; sin prueba
valida el cuerpo no alcanza el pipeline. Comun: body-limit, leer una vez,
errores sin secretos, log sin tokens/firmas, pipeline en background con
timeout.

GitHub (POST /webhook/github, /api/github/webhook): con secreto exigir firma
valida (401 si falta/invalida; solo sha256= a futuro; compare_digest); SIN
secreto RECHAZAR (401/503), solo permitir sin secreto en loopback con flag
explicito allow_insecure_github_local. Current: if secreto and ... -> sin
secreto procesa igual (test_github_sin_secreto_acepta_sin_firma). Arranque
no-loopback sin secreto deshabilita la ruta.
Telegram (POST /webhook/telegram): declarar "confianza por URL secreta, sin
autenticidad criptografica". Objetivo: exigir token (actual) + secret_token de
Bot API (X-Telegram-Bot-Api-Secret-Token fijado en setWebhook) como frontera;
sin el solo loopback o deshabilitado fuera de loopback; allowlist chat_id
opcional. Nunca presentarlo como autenticado sin secret_token.

firmada, metricas, TLS en el gateway (delegado al reverse-proxy).

## 11. Security invariants (normativos)

A-Authentication: toda capacidad remota sensible exige auth acorde a su
boundary (excepciones enumeradas: health minimo). B-Authorization: auth no
concede capacidades; cada operacion se autoriza por capacidad secc. 5.
C-Execution: ninguna operacion remota ejecuta fuera de la politica secc. 6
(allowlist remota + default-deny + rechazo; nunca shell=True remoto).
D-Filesystem: ninguna operacion escapa del boundary (traversal/symlink/TOCTOU/
camino alternativo); escritura solo escribir_archivo_seguro, lectura solo via
central. E-Central enforcement: auth/autorizacion/comandos/filesystem en
puntos centrales (Depends FastAPI, dispatcher WS, policy helpers); anadir un
endpoint sin ellos = fallo de seguridad. F-Fail closed: credencial/config
ausente/corrupta/ambigua -> denegar o rehusar arrancar, nunca abrir/ejecutar.

## 15. Architectural decision (con rationale)

1. Trust: loopback/LAN/Internet + webhooks GitHub/Telegram/Discord separados.
   Alcanzabilidad y criptografia distintas impiden politica unica.
2. Bind: 127.0.0.1 por defecto; salida explicita y condicionada. Evita que un
   flag casual abra RCE a la LAN.
3. Auth: misma key HTTP+WS, header primario, query deprecated; sin clave
   generar+exigir en loopback, abortar fuera; WS pre-accept 1008. Reutiliza lo
   existente, cierra fail-open y asimetria H1a sin PKI en M1.
4. Authz por capacidad en dispatcher central; plugin_install alto privilegio.
   Parchear run no basta (H1b): solo el mapeo previo es estructural.
5. Ejecucion remota B+C: allowlist remota SUBCONJUNTO mas restrictiva +
   rechazo, nunca sandbox silencioso ni shell=True. En red no hay humano ni
   Docker; pip/npm/python/curl son seguros-ante-humano, no ante-red.
6. Filesystem con enforcement unico (resolver->validar->escritura segura);
   directorio = input atacante. H2 muestra que lo por-handler se evade; H3 que
   lo central funciona.
7. Enforcement central (Depends, dispatcher WS, helpers). Unico modo de que
   futuros endpoints no reintroduzcan H1b/H2.
8. /ws/interactive: misma auth + capacidad propia, solo loopback en M1.
   Maximo poder (hub ReAct), minima proteccion hoy: restringir primero.
9. Webhooks: GitHub rechaza sin secreto (flag local explicito aparte);
