## 5. Trust model review

Loopback/LAN/Internet+proxy/webhooks-por-proveedor: esqueleto suficiente. Gaps: reverse-proxy local, Docker bridge, VM, port-forward, SSH-tunel, Tailscale/VPN convierten loopback en alcanzable sin cambiar host. B9.58 mitiga (key incluso en loopback) pero GET / y health publicos en loopback y "Telegram sin secret solo loopback" se vuelven inseguros si hay reenvio. Falta invariante: loopback es interfaz, no prueba de proximidad; reenvio == LAN. Navegador victima citado sin decision CSRF. Telegram degradado a confianza por URL secreta: honesto y correcto. Sin clausula reenvio==LAN, port-forward/SSH-tunel rompen el contrato. Gap severidad Alta.

## 6. Bind/auth review

127.0.0.1+auth+fail-closed+opt-in coherente. Generar+exigir reutiliza _clave_api_efectiva; B9.58 exige cerrar el ->"" : correcto. Pendiente BLOCKING: exposicion unica de clave generada, permisos config.json, rotacion, no-log (print actual filtra). _generar_clave_api usa token_urlsafe(32): OK; falta entropia minima para --api-token manual. ?api_key= deprecated pero necesario para WS: B9.58 lo conserva deprecated, correcto. arrancar_api hoy no valida: gap implementacion, no contrato.

## 7. Authorization review

Puede un futuro handler saltarse la politica? Hoy si; con contrato solo si se implementa invariante E (mapa request->UNA capacidad ANTES de ejecutar, sin mapeo->denegar, Depends + dispatcher central, plugin_install alto privilegio). Es estructural, no "recordar llamar": correcto. Residual: sin CAPABILITY_MAP cerrada + test dummy-sin-capacidad->bloqueada (criterio 9) un add_api_route/elif nuevo olvida el mapeo. Exigir registro unico. Threading modo-remoto hasta _ejecutar_comando: BLOCKING.

## 8. Remote execution review

Decision allowlist_remota SUBCONJUNTO CLI + prohibidas + rechazo + sin sandbox silencioso: precisa e implementable. Rechazo de A (reutilizar CLI: pip/npm/pytest/git ejecutan codigo) correcto. Cubre shell=True prohibido, pipes/;/backticks/$()/redirecciones fuera de directo, interpretes y curl/wget denegados. Cerrar en implementacion: PATH manipulation (exigir resolucion absoluta + env cerrado), wrappers/symlinks del binario, args peligrosos (git -c, pip --index-url), binarios dual-use (B9.58 ya los excluye, mantener). Comando-vs-accion bien planteado (run==tarea/fix/plan). Suficiente; PATH/argv BLOCKING menor.

## 9. Filesystem review

Principio resolver->validar->operacion segura con punto central es convertible en boundary unico. Alternativos hoy: dependencias/semantica/explorar/tarea/accion/tarea_api con directorio crudo; lectura sin O_NOFOLLOW; TOCTOU; daemon/tasks/plugins/MCP indirectos. B9.58 los enumera y exige centro + prohibe delete/rename/chmod: correcto. Capacidad que toque FS sin boundary? Hoy si; con contrato solo si daemon/plugin/MCP quedan fuera — el contrato los incluye. Falta explicitar que tareas background heredan boundary validado (no re-resuelven crudo). Aclaracion BLOCKING menor.

## 10. WebSocket review

/ws/interactive (inyecta al hub ReAct, maximo privilegio) con misma auth + capacidad propia + solo loopback M1: coherente (restringir primero lo mas poderoso). Equivalentes fuera de localhost: /ws tarea/run/fix/plan/search + POST query/plan/chat/daemon + webhooks->pipeline. B9.58 las cubre con misma auth+capacidad; asimetria interactive DENY vs tarea LAN-permitida justificable (hub+contenido arbitrario al editor). Documentar rationale. Ciclo 1008/1009/1011 y manejo malformado/desconocido coherente.
## 11. Webhook review

GitHub: HMAC sha256 (fallback sha1) compare_digest; sin secreto RECHAZAR 401/503 + flag local + deshabilitar no-loopback sin secreto. Correcto. Mantener promesa solo-sha256 futuro.
Telegram: secret_token + token local; sin el solo loopback/deshabilitado. Honesto (sin firma, confianza por URL secreta). Limites expuestos: URL conocida inyecta Updates; secret sin replay interno; falta allowlist chat_id opcional. PASS condicional.
Discord: Ed25519 ambas cabeceras, 503 sin clave, 401 mala, body-limit, 400 JSON, PING sin pipeline. Correcto salvo anti-replay: ventana ~5min propuesta pero verify_signature no valida timestamp. Criterio 8 no verificable sin diseno reloj/skew/store. NEEDS CLARIFICATION (BLOCKING menor).

## 12. HTTP hardening review

M1 obligatorio (TrustedHost, size-limits+timeouts, 4xx sin traceback incl. Discord json.loads, no-log, query deprecated): bien. M1 recomendado (rate-limit, headers, docs fuera loopback): aceptable, pero rate-limit en auth es necesario para 401 seguro contra fuerza bruta — dependencia circular parcial. Subir rate-limit auth/webhooks a obligatorio basico en memoria o declarar riesgo. CORS ausente==same-origin y NO anadir CORS(*): correcto. TLS via proxy + prohibir HTTP plano M1: coherente.

## 15. Open decisions classification

1. nombre/contenido sandbox_allowlist_remota: BLOCKING (sin ella run remoto indefinido; fail-closed la deja en denegar-todo, pero M1 necesita contenido minimo + proceso auditoria vs ALLOWLIST CLI).
2. raiz por defecto no-loopback: BLOCKING (cwd implicito fuera de loopback = traversal amplificado; exigir raiz explicita o abortar).
3. allowlist chat.proveedor: NON-BLOCKING (coste/SSRF via proveedor/modelo arbitrario; fijar default seguro + lista, no bloquea auth/boundary).
4. visibilidad tasks: BLOCKING (lectura transversal de tareas ajenas + TOCTOU boundary; definir owner==credencial o DENY no-loopback).
5. visibilidad daemon: BLOCKING (iniciar/detener remoto = persistencia; definir DENY no-loopback M1 o capacidad separada + confirmacion).
6. ventana replay Discord: NON-BLOCKING (endurece, no habilita; ship sin ella con rate-limit, anadir despues con diseno reloj/store).
7. rate limits: BLOCKING parcial (valores CAN DEFER con medicion; existencia de limit basico auth/webhooks BLOCKING por §12).

Conclusion: NO listos para implementacion hasta cerrar 1,2,4,5 (+credencial store/rotacion §6, CAPABILITY_MAP §7, PATH/argv §8, boundary background §9, replay-diseno §11, proxy==LAN §5).

## 16. Missing decisions (solo con evidencia de codigo)

- Credencial generation/storage/rotation: _clave_api_efectiva genera+guarda+print; falta entrega unica, permisos, rotacion, no-log. BLOCKING.
- Authorization model registry: falta CAPABILITY_MAP cerrada + prohibicion rutas fuera del factory. BLOCKING.
- Privilege separation plugin_install/marketplace (descarga codigo+ejecucion): incluido como capacidad pero sin sandbox/firma/revision. NON-BLOCKING M1 si DENY no-loopback.
- Error semantics: Discord json.loads sin try->500; WS continue silencioso tipo desconocido. B9.58 lo cubre (400/4xx tipados): mantener, no falta.
- Audit logging sin secretos (quien/capacidad/decision/rechazo): necesario para detectar bypass; hoy inexistente. NON-BLOCKING (minimo en M1).
- Session lifetime WS reconnect: re-auth por conexion (ya pre-accept) + rate por conexion; falta tope hilos/cola y cierre tras N violaciones (B9.58 lo propone): aclarar valores CAN DEFER.
- CSRF: UI estatica + WS con ?api_key= + sin Origin check => navegador victima puede abrir WS loopback si la key esta en URL/historial. Con key en header no hay CSRF clasico, pero ?api_key= lo reintroduce. Decision faltante real: validar Origin/Host para /ws en loopback o eliminar query salvo compat. BLOCKING menor.
- Proxy trust / Host header: sin TrustedHost, X-Forwarded-For/Host no confiables; B9.58 exige TrustedHost basico M1: correcto, no falta.
- MCP tools como camino FS/exec indirecto (mcp_tools*.py existen): B9.58 menciona MCP una vez; falta mapear herramientas MCP a capacidades/boundary. NON-BLOCKING (inventariar en M1).

No se anade lista generica (mTLS/WAF/SIEM quedan fuera M1 correctamente).
