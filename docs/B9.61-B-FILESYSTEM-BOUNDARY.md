# B9.61-B — Filesystem Boundary (implementación + correcciones B9.61-B-R)

> Documento de referencia de la implementación. No es una auditoría: la
> revisión independiente es **B9.61-B-R** y sus correcciones son
> **B9.61-B-CORRECTION**. Sin commit/push.

## 0. Cadena real (post-correcciones)

```text
request input (ruta, directorio, tema, origen)
    ↓
server workspace root          ← la fija el SERVIDOR, nunca el request
    ↓
filesystem boundary            ← web/filesystem.py (resolve → containment → política)
    ↓
operation                      ← read (O_NOFOLLOW) / write (C3) / cwd / exploración
```

`directorio` es **input atacante** (B9.58 §7): solo puede interpretarse como
subruta de la raíz del servidor. Nunca la sustituye.

## 1. Frontera central

`web/filesystem.py` es el **único** punto por el que pasa toda ruta del
filesystem controlada por el cliente:

| Primitiva | Uso |
| --- | --- |
| `Frontera.raiz_efectiva` | raíz de seguridad vigente (fail-closed si no hay) |
| `Frontera.base_operacion` | resuelve/valida `directorio` contra la raíz |
| `Frontera.resolver_ruta` | resuelve una ruta relativa dentro de la base |
| `Frontera.resolver_cwd` | `cwd` de subprocesos ya validado |
| `Frontera.leer` | lectura segura (`O_NOFOLLOW`) |
| `Frontera.escribir` | delega en C3 (`utils.escribir_archivo_seguro`) |
| `resolver_raiz_workspace` | valida/congela `--workspace-root` |
| `raiz_servidor_por_defecto` | raíz del servidor para loopback (F-01) |

## 2. Workspace root

* **Con `--workspace-root`** (obligatorio en LAN/Internet): raíz congelada a su
  `realpath`. Ausente o inválida fuera de loopback → el arranque **aborta**
  (`WorkspaceRootInvalido`). Nunca se degrada a cwd, `/`, `/home` ni un temporal.
* **Loopback sin `--workspace-root`** (F-01): la raíz es la del **servidor**
  (`resolver_raiz(".")`: cwd/repo), resuelta y congelada al arrancar. Antes el
  `directorio` del request definía la frontera, lo que permitía leer `/etc/passwd`
  y escribir en `/tmp` con una credencial válida.
* Raíces **nunca** válidas: `/`, `/home`, `/root`, `/Users`, el home del usuario
  y sus ancestros; también inexistentes, no-directorio, sin permisos o symlinks
  rotos.
* Una raíz dada como symlink se resuelve: la raíz efectiva es su `realpath`; si
  ese `realpath` cae en una raíz prohibida, se rechaza.
* **`--workspace-root` debe ser absoluto** (F-04): una ruta relativa depende del
  cwd del proceso y no es una frontera estable.

Comportamiento de `directorio` con raíz del servidor `/srv/app`:

| `directorio` | Resultado |
| --- | --- |
| `null` / `"."` | `/srv/app` |
| `"src"` | `/srv/app/src` |
| `"/etc"`, `"/tmp"`, `"/root"` | **DENY** `outside_workspace` |
| `".."` | **DENY** `outside_workspace` |

## 3. Resolución de rutas

Rutas relativas a la base; se rechazan absolutas, `~`, byte nulo y cualquier
componente `..` (aunque la ruta normalizada seguiría dentro). El traversal
codificado en URL (`%2e%2e%2f`, doble codificación, `file://`) se rechaza
decodificando y comparando la forma resultante. La contención se evalúa **sobre
la ruta resuelta** comparando componentes (`_contener`), nunca con
`str(...).startswith(...)`.

## 4. Symlinks

La contención se hace sobre el `realpath`: un symlink de archivo, directorio,
anidado, de padre o roto que apunte fuera de la raíz se deniega. Un symlink
**dentro** de la raíz se permite y se resuelve a su destino real. El
`directorio` en sí mismo pasa por la misma comprobación.

## 5. Inputs con validación propia (no son rutas)

Dos entradas del request llegan a operaciones que **no** son de resolución de
rutas, y por eso tienen su propia validación:

### `tema` (`explorar`) — F-02

`tema` es un **argumento de búsqueda**, no una ruta. Antes se interpolaba en un
f-string con comillas dobles (`rg ... "{tema}"`) y se ejecutaba con `shell=True`,
lo que permitía `"; cat /tmp/X; echo "`. Ahora se convierte en un argumento
literal con `shlex.quote` (mismo módulo que ya usa el proyecto): llega al
buscador como un único token y nunca como código. **No es una blacklist**: cualquier
metacarácter es válido como contenido de búsqueda.

### `origen` (`plugin_install`) — F-03 / R2-F01

`origen` se clasifica **fail-closed**: ante ambigüedad es una **ruta local** y
pasa por la filesystem boundary. Solo se considera remoto cuando su semántica
remota es explícita e inequívoca.

**Formato remoto reconocido (único): URL con esquema** (`http://`, `https://`).
Es el único caso que `_plugin_descargar_zip` discrimina sin ambigüedad
(`origen.startswith("http")`). Se entrega intacto, sin pasar por la frontera
(no es una ruta del filesystem local).

**Todo lo demás es ruta local** y se canonicaliza **contra la raíz del
workspace** (nunca contra el cwd), con comprobación de containment:

| `origen` | Resultado |
| --- | --- |
| `plugin`, `./plugin` | canonicalizado dentro de la raíz |
| `./user/repo`, `foo/bar`, `foo/bar/plugin`, `user/repo`, `user/repo.git` | canonicalizado dentro de la raíz |
| `../plugin`, `../../plugin` | **DENY** `outside_workspace` |
| `foo/../bar`, `foo/bar/../../outside` | canonicalizado dentro de la raíz (no escapa) |
| `/etc/passwd`, `/tmp/plugin`, `/root/plugin`, `~/.ssh` | **DENY** `outside_workspace` |
| symlink que apunta fuera | **DENY** `outside_workspace` |
| ruta relativa que **no existe** ni bajo la raíz ni bajo el cwd | se devuelve el texto (preserva el slug remoto histórico) |

**No se usa como criterio de remoto** ninguna propiedad sintáctica: número de
segmentos, presencia/ausencia de extensión, profundidad, cantidad de `/`, ni las
formas `user/repo`, `foo/bar`, `./x` o `a/b/c`. Cualquiera de ellas es también
una ruta filesystem válida, por lo que no prueba el origen. La heurística
anterior (B9.61-B-CORRECTION) clas `./PLUG_R2_E2E` y `foo/bar/plugin` como
remotos, con lo que evitaban la frontera y `_plugin_leer_manifest` leía fuera
del workspace; la corrección lo cierra comprobando **también** la resolución
contra el cwd del proceso, que es como `sc._plugin_instalar` resuelve las rutas
relativas.

`web/app.py` no contiene llamadas directas a `open/read_text/write_text/rglob/
glob/iterdir/mkdir/unlink/shutil` (invariante verificado por test sobre el
código, no sobre los docstrings).

## 7. Capabilities y errores

* La relación se mantiene: `authentication → capability → frontera → operación`.
  No se crean capabilities nuevas ni se modifica `CAPABILITY_MAP` (B9.61-A).
* Denegaciones: `ErrorFrontera` (subclase de `ValueError`, por compatibilidad
  con la convención de `_validar_ruta_segura`) con código estable
  (`invalid_path`, `outside_workspace`, `not_found`, `permission_denied`,
  `symlink`). El mensaje público nunca contiene rutas absolutas reales, secretos
  ni configuración interna; el log del servidor sí registra el código.

## 8. C2 y C3 preservados

* **C2** (`sandbox_utils.clasificar_comando`) intacto: `_ws_clasificar_run` no se
  toca. Este bloque no implementa la política de allowlist remota.
* **C3** (`utils.escribir_archivo_seguro`) intacto: la frontera solo decide qué
  ruta relativa se le entrega. `O_NOFOLLOW`, `O_EXCL` y la verificación de padre
  seguro siguen siendo la última línea de defensa.

## 9. Límites conocidos (no cerrados aquí)

* La política de comandos remota (`sandbox_allowlist_remota`, validación de argv
  de `run`) es trabajo de B9.61-C. `_ws_clasificar_run` solo delega en C2.
* El origen remoto de plugins (descarga, `pip install`) y el contexto congelado
  completo de tasks (root + capabilities + policy) pertenecen a B9.61-C.
* La raíz del servidor en loopback es el cwd/repo del proceso: si el gateway se
  arranca desde un directorio demasiado amplio, esa raíz lo refleja. Para
  deployments no loopback `--workspace-root` es obligatorio y valida la raíz.
