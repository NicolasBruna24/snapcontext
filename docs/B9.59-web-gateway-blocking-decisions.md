## 3. Remote command allowlist decision

"Comando permitido" remoto = conjuncion: (a) sin metacaracteres amplios + shlex valido; (b) binario base en sandbox_allowlist_remota; (c) ejecutable real resuelto con PATH cerrado del servidor (which sobre env fijo, O_NOFOLLOW, realpath); (d) argv validado por regla por-binario (flags con =, -c/-e/--exec/--index-url, red o path fuera del workspace -> denegar); (e) no en categorias prohibidas aunque este en CLI. Identidad = nombre + ruta absoluta + argv normalizado. Interpretes (python*, node, ruby, sh, bash, pwsh), red (curl, wget) y shell compuesto: prohibidos siempre. pytest/npm/pip/git prohibidos por defecto (ejecutan codigo o red); solo subcomandos de solo-lectura auditados (git status/diff/log, pip list, npm ls), nunca install/run/test/checkout. Wrappers/scripts/symlinks: se valida el ejecutable final (shebang a interprete prohibido -> denegado). SUBCONJUNTO = inclusion estricta verificable por test; vacia/ausente = denegar todo run; sin fallback a sandbox.

## 4. Filesystem root decision

Raiz = base que confina TODAS las operaciones Web. localhost -> resolver_raiz actual aceptable. LAN/Internet -> raiz EXPLICITA obligatoria (--workspace-root o config); ausente = rehusar arrancar. Nunca validas: /, /home, /home/usuario, %USERPROFILE%, symlink sin resolver, inexistente. Raiz invalida -> error fatal, nunca degradar a cwd. directorio dentro de raiz o denegar. localhost: cwd/repo con boundary. LAN: raiz explicita confinada. Internet M1: DENY (HTTP plano prohibido; solo tras proxy declarado + misma raiz explicita). Tasks heredan raiz congelada; daemon no cambia de raiz entre ticks.

## 5. Tasks decision

Superficie real: crear, leer estado/resultado, ejecutar (git checkout+pytest, flujo_principal --auto, _ejecutar_planificador), programar, persistir en memoria.db, FS/red/procesos, notificar Telegram/Discord. Sin owner: cualquier key lee cualquier task_id. M1: MANAGE_TASKS propia, autenticada, SOLO LOCALHOST (crear y leer); fuera de loopback -> 403/404. Requiere owner = credencial creadora (ajena -> 404 sin oraculo), raiz y politica congeladas (secc.10), tipos solo query/plan (no tests/pr_review con checkout/red salvo allowlist futura).

## 6. Daemon decision

Capacidad real (api_daemon + _bucle_daemon -> sc._daemon_tick periodico): hilo persistente que sobrevive al request, hereda permisos/FS/red del servidor, ejecuta ticks diferidos con intervalo desde el request. M1: opcion B — SOLO LOCALHOST. estado autenticado en loopback; iniciar/detener localhost-only con MANAGE_DAEMON separada; fuera de loopback -> denegado. Hereda: auth+capacidad del creador, raiz congelada (secc.4), politica remota (secc.3), lifecycle ligado al servidor (sin autoarranque remoto; intervalo acotado validado). Justificacion: estado es lectura inocua; iniciar/detener remoto = persistencia + ejecucion diferida fuera de contexto auditado.
## 7. Capability model decision

Capacidades cerradas M1: READ_WORKSPACE, WRITE_WORKSPACE, EXECUTE_REMOTE, MANAGE_TASKS, MANAGE_DAEMON, USE_PLUGINS, USE_INTERACTIVE, USE_CHAT, WEBHOOK_RECEIVE (por proveedor). Mapeo: query/plan->EXECUTE_REMOTE (+WRITE si aplica); chat->USE_CHAT (+EXECUTE si ejecuta); skills->READ; tasks/id->MANAGE_TASKS; daemon estado->READ+auth, iniciar/detener->MANAGE_DAEMON; ws tarea/fix/review/plan/search/run->EXECUTE_REMOTE (+WRITE/READ segun subop); leer->READ; guardar->WRITE; dependencias/semantica/explorar->READ; interactive->USE_INTERACTIVE; webhooks->WEBHOOK_RECEIVE (sin heredar otras). Enforcement: CAPABILITY_MAP cerrada en el factory; Depends central (HTTP) y dispatcher central (WS) resuelven capacidad ANTES de ejecutar; sin mapeo -> denegar; prohibido registrar rutas o elif fuera del centro. Test de invariancia (conceptual): ruta/tipo dummy sin pasar por el centro -> bloqueo verificado HTTP+WS. localhost-only: MANAGE_TASKS, MANAGE_DAEMON, USE_INTERACTIVE, USE_PLUGINS. LAN-permitidas con auth: READ, WRITE, EXECUTE_REMOTE (+boundary+allowlist), USE_CHAT. Prohibidas remoto M1: plugins/interactive/daemon-iniciar/tasks no-loopback.
## 8. CSRF decision

Sin cookies (key por header X-API-Key o query ?api_key=; sin Set-Cookie/sesion): CSRF clasico por cookie NO aplica a API ni webhooks (HMAC/Ed25519/secret_token no autoenviados). Riesgo navegador: UI estatica + /ws aceptando ?api_key= en URL (historial/logs) sin Origin-check. M1: (1) prohibido auth por cookie; (2) sin CSRF-token (sin cookies no aporta); (3) Origin/Host-check obligatorio en /ws y /ws/interactive (origen mismo host/puerto; ausente -> denegar en no-loopback, permitir+log en loopback con key valida); (4) ?api_key= solo compat WS, nunca en docs, con warning; (5) /ws/interactive hereda lo anterior + localhost-only. Decision basada en el modelo elegido, no en checklist.

## 9. Credential lifecycle decision

Generation: sin api_key en loopback -> generar secrets.token_urlsafe(32) y persistir; no-loopback sin clave -> rehusar arrancar. Manual --api-token <32 chars -> advertencia y rechazo en no-loopback. Storage: config.json clave api_key con 0600 existente (Unix 0600 / Windows solo-propietario); sin keyring M1 (sobrecoste injustificado); env SNAPCONTEXT_API_KEY como override sin persistir. Rotation M1: manual (regenera, invalida anterior de inmediato, cierra WS con key vieja <60s, muestra nueva UNA vez por stdout); key vieja -> 401/1008 siguiente request/mensaje; sin doble-ventana M1 (diferido). Exposure: nunca en logs/errores/docs/openapi/URLs salvo entrega unica inicial y ?api_key= compat; errores genericos sin oraculo; el print actual que vuelca la clave se sustituye por aviso sin secreto.

## 10. Background inheritance decision

Al crear task/background se congelan e inmutabilizan: raiz resuelta + directorio validado (relativa confinada, nunca crudo), conjunto de capabilities del request (interseccion, nunca ampliacion), execution policy (modo-remoto + allowlist secc.3), identidad del creador (owner de la credencial, no el secreto), proveedor/modelo validado. Worker revalida contra lo congelado antes de ejecutar; campo ausente/corrupto -> abortar (fail-closed). Prohibido: re-resolver directorio crudo, heredar PATH/env del request, elevar capacidades, ejecutar tipos no permitidos, sobrevivir a rotacion de clave (pendientes de key vieja -> cancelada-por-rotacion antes de ejecutar). Cierra F2/F7/F9 de B9.58-R.

## 11. Localhost forwarding decision

Bind localhost NO equivale a remoto-imposible. Toda proteccion que dependa de "solo loopback" (interactive/daemon/tasks/plugins DENY, Telegram sin secret solo loopback, endpoints publicos) trata cualquier reenvio (port-forward, SSH-tunel, reverse-proxy, Docker bridge/host, VM compartida, VPN) como LAN. Responsabilidades: servidor -> exigir auth incluso en loopback para capacidades sensibles (ya decidido B9.58 secc.2A), log EXPOSING/NON-LOOPBACK-EQUIVALENT si detecta X-Forwarded-For/Forwarded o Host no-local, TrustedHost basico M1; operador -> declarar exposicion y proveer TLS fuera del gateway, nunca HTTP plano; autenticacion -> misma key dentro/fuera (sin modo debil loopback); el reenvio implicito nunca otorga mas privilegio que LAN. Sin infraestructura externa nueva.
