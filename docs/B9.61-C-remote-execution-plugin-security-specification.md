## 1. Objetivo y alcance

Diseñar dos fronteras explícitas para que una entrada remota nunca convierta
`datos` en `ejecución arbitraria de código local`:

```text
A) entrada remota → comando → proceso local
B) entrada remota → referencia de plugin → descarga → filesystem → instalación → ejecución
```

**In scope (especificado aquí)**: identidad de comando remoto, PATH cerrado,
shells e intérpretes, argv estructurado, allowlist remota, cwd, entorno,
red, modelo local/remoto de plugins, descargas, extracción de archivos,
manifests, `pip install`, capacidades, identidad, tasks y rotación de
credencial.

**Out of scope (implementación, no aquí)**: reescribir el instalador de plugins,
el extractor de archivos, la allowlist, el contexto de tasks, la rotación, un
sandbox de red o restricciones de `pip`. Especificados, no construidos.

## 2. Principio central

> **Una operación remota nunca hereda automáticamente los permisos de una
> operación local.**

```text
LOCAL POLICY   ⊃   REMOTE POLICY
```

Que un binario esté en `ALLOWLIST_BINARIOS_DEFECTO` (política local, C2) **no**
implica que sea ejecutable remotamente. Hoy ambas share el mismo conjunto de
nombres, y `clasificar_comando` decide por `basename`; esa
identidad es insuficiente (§4).

La política remota es **explícita, cerrada, fail-closed, capability-bound y
filesystem-bound**.

## 4. Identidad de comando remoto

La identidad **no** es el basename. Es un triple verificado:

```text
IDENTIDAD = (nombre_lógico, ruta_absoluta_resuelta, argv_normalizado)
```

Reglas:

1. **Resolución antes de autorizar**: `argv[0]` se resuelve a una ruta absoluta
   **antes** de cualquier comparación con la allowlist. La comparación ocurre
   sobre la ruta resuelta, nunca sobre el texto del argv.
2. **Verificación de la ruta resuelta**: debe ser un archivo regular, ejecutable
   por el proceso, y no un symlink (o, si lo es, su `realpath` debe seguir
   dentro de un directorio de sistema del `PATH` cerrado — §5).
3. **`argv_normalizado`**: lista de strings, sin metacarácters de shell, con
   flags normalizados a forma explícita. Un flag con valor inline (`--index-url=…`)
   debe rechazarse salvo que esté en la política.
4. **Denegación si la identidad no puede establecerse**: resolución ambigua,
   ejecutable ausente, argv no parseable → `DENY`, nunca fallback.

**Prohibido** usar como identidad: `basename`, resultado de `PATH` sin verificar,
o el texto crudo del comando.

## 5. PATH cerrado

El PATH remoto **no** es `os.environ["PATH"]`. Es una constante de política:

```text
PATH_REMOTO = (/usr/local/sbin, /usr/local/bin, /usr/sbin, /usr/bin, /sbin, /bin)
```

Requisitos:

* **Resolución explícita**: `shutil.which(argv[0], path=PATH_REMOTO)`. Nunca con
  el entorno heredado.
* **Absolute-requirement**: un `argv[0]` con separadores (`./x`, `sub/x`,
  `/tmp/x`) se rechaza **antes** de resolver; solo se acepta un nombre desnudo
  presente en `PATH_REMOTO`.
* **Verificación post-resolución**: la ruta resuelta debe estar bajo uno de los
  directorios de `PATH_REMOTO` tras `realpath`, ser un archivo regular y tener
  permiso de ejecución.
* **Registro**: la ruta absoluta real autorizada se registra en el log de la
  operación (no en la respuesta al cliente salvo que sea informativa).
* **Entorno contaminado**: si `PATH_REMOTO` estuviera contaminado, se rechaza el
  arranque (§13).

Análisis de vectores:

| Vector | Mitigación |
| --- | --- |
| **PATH hijacking** (prepender un dir con un binario falso) | `PATH_REMOTO` constante; `os.environ["PATH"]` ignorado |
| **Binary replacement** (escribir en `/usr/local/bin/x`) | fuera del alcance del atacante remoto; mitigado por verificación de directorio del sistema y, si procede, por propiedad/permisos del root |
| **Symlink executable** | `realpath` debe caer bajo un directorio de `PATH_REMOTO`; un symlink a `/tmp/x` se rechaza |
| **Relative executable** (`./x`, `sub/x`) | `argv[0]` con separador → `DENY` antes de resolver |
| **Working-directory executable** | cwd no se antepone al PATH; `./` nunca se busca |
| **`PATH` como variable de entorno** | se inyecta `PATH=PATH_REMOTO` en el env del proceso (§13) |

## 6. Shells e intérpretes

**Política por defecto: `DENY`**, sin excepciones en M1.

Lista explícita de `DENY` por identidad: `sh`, `bash`, `zsh`, `fish`, `dash`,
`ksh`, `csh`, `cmd`, `cmd.exe`, `powershell`, `pwsh`, `python`, `python3`,
`pythonw`, `perl`, `ruby`, `node`, `npm`, `npx`, `pip`, `pip3`, `uv`,
`poetry`, `env`, `xargs`, `eval`, `exec`, `source`, `find`, `xargs`.

Esto incluye las formas indirectas:

```text
bash -c "..."      sh -c "..."      python -c "..."      node -e "..."
python -m pip …     perl -e "…"      ruby -e "…"
```

Un intérprete **nunca** puede usarse como atajo para ejecutar un comando
diferente del autorizado. Si en el futuro se autorizara un intérprete (p. ej.
para una herramienta de análisis), requiere:

1. Decisión ratificada explícita (§30, OD-3).
2. Una política de argv completa y por subcomando, no un permiso genérico.
3. Un sandbox real y no solo "sandbox Docker ausente → abortar".

Nota: `xargs`, `env`, `find` y `eval`/`exec`/`source` **ejecutan lo que les
pasan**; deben ser `DENY` en remoto, no "sandbox".

## 7. Metacarácters de shell

La autorización remota **no** se basa en detectar metacarácters. La defensa
principal es:

```text
argv estructurado (list[str])
+ shell=False siempre
+ allowlist exacta por identidad
```

Consecuencia arquitectónica: **la política remota no tiene una vía `shell=True`**.
Si un comando trae metacarácters, no se "sanea": se **rechaza**, porque
`shell=True` es lo que amplía la semántica.

Los filtros de metacarácters (`_METACARACTERES_AMPLIOS`,
`tiene_metacaracteres_shell`) se conservan **solo** como defensa secundaria y
para el camino local/CLI. No son frontera en remoto.

## 8. Allowlist remota

Allowlist **cerrada, versionada y explícita**, distinta de la local. Clave de
config nueva: `sandbox_allowlist_remota` (B9.59 §3 la ya nombró).

**Ausente, vacía o corrupta ⇒ `DENY ALL`.** Sin fallback a
`ALLOWLIST_BINARIOS_DEFECTO`, sin fallback al sandbox, sin fallback a modo
local. El arranque con política remota vacía es válido (servidor que no ejecuta
nada), pero cualquier intento de ejecutar ⇒ denegado.

Cada entrada define, como mínimo:

```yaml
- id: git-status
  binario: git
  ruta_resuelta: /usr/bin/git        # prefijo aceptado
  argv_permitidos: [status, diff, log, show, branch, rev-parse]
  argv_prohibidos: [clone, fetch, pull, push, checkout, reset, clean, config, remote, ...]
  flags_prohibidos: ["--exec", "--upload-pack", "--receive-pack", "-c", "--config-env"]
  requisitos_filesystem: [lectura]
  requisitos_red: ninguno
  capability: EXECUTE_REMOTE
  subcomandos_anidados: [...]        # p.ej. git log --follow
```

Reglas transversales:

* Un flag que reciba código o URL (`-c`, `--exec`, `--index-url`, `--exec-path`)
  se rechaza salvo que esté enumerado explícitamente.
* Cualquier argumento que sea una ruta absoluta o que escape del workspace ⇒ DENY.
* Un path o argumento que apunte fuera del workspace ⇒ DENY.
* Flags de red (`--upload`, `--remote`, `--dry-run` no aplica) ⇒ DENY salvo
  excepción enumerada.
* La identidad includes la ruta resuelta: mover o sustituir el binario invalida
  la coincidencia.

## 9. Git

`git` **no** es "seguro" por ser VCS. Desglose:

| Subcomando | Remoto M1 | Motivo |
| --- | --- | --- |
| `status` | permitido | lectura del workspace, escribe `.git/index` (dentro) |
| `diff` | permitido | lectura; `--output` debe rechazarse |
| `log` | permitido | lectura; sin `--exec` |
| `show` | permitido | lectura |
| `rev-parse` | permitido | lectura |
| `branch` | **DENY** | `--edit-config` escribe config; permite `-f`/`-D` destructivo |
| `clone` | **DENY** | red + escritura arbitraria + hooks del repo clonado |
| `fetch` / `pull` | **DENY** | red + hooks post-merge/checkout ejecutan código del repo |
| `push` | **DENY** | red + exfiltración |
| `checkout` / `switch` | **DENY** | ejecuta hooks; escribe fuera del index simple |
| `reset` | **DENY** | destructivo |
| `clean` | **DENY** | destructivo |
| `config` | **DENY** | escribe config; puede apuntar a rutas/hooks |
| `remote` | **DENY** | modifica remotos (red + config) |
| `worktree`, `submodule`, `stash`, `gc`, `fsck` | **DENY** | hooks, escritura amplia o plugins |

Razón de fondo: git ejecuta **hooks** y **filtros** configurables, por lo que
casi cualquier subcomando con escritura es un vector de ejecución.

**Conclusión**: el subconjunto remoto permitido es
`{status, diff, log, show, rev-parse}`, y solo si los flags están enumerados.
Si el producto no los necesita, la recomendación es `DENY ALL` para git.

## 10. Pytest

**Política: `DENY`.**

`pytest` **ejecuta código Python del proyecto**: `conftest.py`, fixtures,
`pytest_plugins`, hooks de `pytest.ini`/`pyproject.toml`, y cualquier
`import` de los módulos bajo prueba. Para un atacante remoto equivale a
`python` con cwd en el workspace — es decir, ejecución arbitraria. No es una
"herramienta de testing inocua" en este modelo.

Aunque hoy `ALLOWLIST_BINARIOS_DEFECTO` incluye `pytest`, eso es **política
local**. En remoto se rechaza.

Excepción: solo con sandbox real, workspace de solo lectura y decisión
ratificada (OD-4). No en M1.

## 11. Gestores de paquetes

**Política: `DENY` por defecto** para `npm`, `npx`, `pip`, `pip3`, `uv`,
`poetry`, `yarn`, `pnpm`, `gem`, `cargo install`.

Razones: instalación de código de terceros; **supply chain** (un paquete puede
publicar versión maliciosa); **scripts post-install** que se ejecutan con
privilegios del proceso; **acceso a red** arbitrario; **escritura fuera del
workspace** (site-packages, `--user` → home); **exposición de credenciales**
del entorno; y capacidad de ejecutar código durante la resolución.

Excepciones (`npm ls`, `pip list`) siguen sin ser recomendables en remoto
porque el mismo binario, con otro subcomando, instala; el control real es la
allowlist por subcomando, no el binario. Si se admiten, deben ir en entradas
propias con `argv_permitidos` cerrado.

## 12. Frontera de filesystem del comando remoto

```text
cwd         = Frontera.resolver_cwd(directorio)     # ya implementado en B9.61-B
workspace   = Frontera.raiz_efectiva()              # congelada al arranque
```

Reglas:

* El `cwd` **nunca** es una ruta del cliente sin validar: se valida por la
  frontera (B9.61-B lo resuelve para `run`).
* Todo argumento que sea ruta debe confinarse a `workspace` antes de
  autorizar el comando (§8).
* Un comando permitido no puede cambiar su propio directorio de forma
  escapando: los flags con ruta (`-C`, `--git-dir`, `--work-tree`, `-f` de
  `grep`) se enumeran o se rechazan.
* Los archivos que el comando escriba quedan en el workspace; **no** hay una
  frontera de solo-lectura por comando en M1 salvo que la entrada lo declare
  (`requisitos_filesystem: [lectura]`) y entonces se ejecuta con un workspace
  montado de solo lectura (fuera de M1 → declarar `DENY`).
* Variables de entorno no pueden redirigir rutas: `GIT_DIR`, `GIT_WORK_TREE`,
  `PYTHONPATH`, `NODE_PATH`, `XDG_CONFIG_HOME` no se pasan (§13).

## 13. Entorno de proceso

El proceso remoto **no** hereda `os.environ`. Se construye un entorno mínimo
construido desde cero:

```text
PATH          = PATH_REMOTO
HOME          = <directorio de trabajo sintético dentro del workspace>
LANG/LC_ALL   = valor fijo
TMPDIR        = <tmpdir dedicado y efímero>
GIT_*         = no presente
XDG_*         = no presente
```

Explícitamente **excluidas** (ausentes, no vacías):

```text
API keys del proveedor (GEMINI_API_KEY, OPENAI_API_KEY, ANTHROPIC_API_KEY,
DEEPSEEK_API_KEY, GROQ_API_KEY, OLLAMA_URL)
SSH_AUTH_SOCK
AWS_*, GOOGLE_*, AZURE_*, GITHUB_TOKEN, GH_TOKEN
LD_PRELOAD, LD_LIBRARY_PATH
PYTHONPATH, PYTHONHOME, PYTHONSTARTUP
NODE_PATH, NODE_OPTIONS
GIT_CONFIG, GIT_CONFIG_GLOBAL, GIT_SSH_COMMAND
BASH_ENV, ENV, IFS
http_proxy/https_proxy (salvo proxy declarado)
```

`HOME` debe apuntar dentro del workspace para que `~` no resuelva al home real
del usuario; combinado con la frontera, un `..` o `~` en un argumento queda
contenido.

Si `PATH_REMOTO` no cumple la verificación de §5, el arranque falla (fail-closed).

## 14. Acceso a red

**Autorización de red separada de la de comando.** Un comando autorizado no
obtiene red por el hecho de estar autorizado.

Clasificación por entrada de allowlist:

| Entrada | Red |
| --- | --- |
| `git status/diff/log/show/rev-parse` | ninguna |
| descarga de plugin | **requerida**, con destino y origen cerrados (§16-17) |
| índice de marketplace | requerida, `GET` a origen declarado |
| cualquier otra | ninguna |

Reglas:

* Por defecto, un comando remoto se ejecuta **sin** capacidad de red
  (namespace de red o egress bloqueado cuando la plataforma lo permita; si no,
  se documenta como limitación explícita y los binarios de red —`curl`, `wget`,
  `ssh`, `nc`, `ftp`— son `DENY`).
* `curl` y `wget` son `DENY` en remoto (ya están en
  `_BINARIOS_SIEMPRE_SANDBOX`, pero sandbox ≠Control de red).
* La descarga de plugins (§16) usa un cliente HTTP dedicado con destinos
  enumerados, no un binario genérico.

## 15. Modelo de plugin: local vs remoto

**Debe existir una representación explícita**, no una heurística de forma.
B9.61-B ya resolvió la ambigüedad en el gateway (fail-closed: `://` → remoto,
resto → local). Esa lógica **debe consolidarse en el modelo de dominio**, no
repetirse por consumidor.

Contrato propuesto (conceptual; implementación en B9.61-C):

```text
OrigenPlugin = { clase: "local",  ruta: <Path canónico bajo workspace> }
             | { clase: "remoto", url: <URL https absoluta> }

InstalableDesde(OrigenPlugin) = (OrigenPlugin.clase == "remoto" and razón de política)
                              or (OrigenPlugin.clase == "local" and ya instalado)
```

Reglas:

* `clase` la determina **el consumidor de la API pública**, no un parseo de
  string. Un caller HTTP/WS elige explícitamente.
* El slug `user/repo` **deja de ser ambiguo**: pasa a ser un caso explícito
  (`proveedor + owner + repo`) o se elimina del gateway remoto. Mientras tanto,
  en remoto `user/repo` **no** se resuelve a filesystem.
* Un `OrigenPlugin` remoto **nunca** se convierte en `Path` antes de pasar por
  la frontera de descarga (§16-18).
* Compatibilidad: las funciones CLI que aceptan strings conservan su
  comportamiento local; el gateway usa la API tipada.

## 16. Fuentes remotas suportadas (catálogo)

Inventario verificado del código actual:

| Formato | Dónde | Tratamiento actual |
| --- | --- | --- |
| `https://…` (codeload/GitHub zip) | `_plugin_descargar_zip` | `urlopen` → `write_bytes` → extracción segura (C-R1-01) |
| `http://…` | `_plugin_descargar_zip` | **DENY** (C-R1-02): ya no es un `RemoteURL` soportado |
| `ftp://`, `file://`, esquema arbitrario | gateway y CLI | **DENY** (`unsupported_origin` / sin abrir red) |
| `usuario/repo` (slug GitHub) | `_plugin_descargar_zip` | validado con regex estricta → `codeload.github.com/{slug}` |
| índice de marketplace | `marketplace.obtener_index` | `urlopen` con URL por defecto/configurable |
| ruta local | `_plugin_instalar` | ya confinada por B9.61-B |

Contrato vigente tras C-R1-01/C-R1-02:

- `RemoteURL` representa **únicamente** `https://…` (`ESQUEMAS_REMOTOS_SOPORTADOS`).
- Cualquier otro esquema es un origen remoto **no soportado**: se deniega y
  nunca se degrada a `LocalPath` (en particular `file://` no es una ruta local).
- La CLI de descarga no hace downgrade a `http` y no entrega a `urlopen` nada que
  no sea una URL `https` validada o un slug GitHub que no controle esquema,
  host, query, fragmento ni traversal.

Requisitos por formato en remoto:

| Propiedad | `https://` | `slug usuario/repo` |
| --- | --- | --- |
| Esquema | **obligatorio** | n/a (se construye https) |
| TLS | verificación de certificado activa; sin fallback a http | hereda https |
| Autenticación | ninguna por defecto; si se añade, token explícito, nunca del `env` del proceso | ninguna |
| Redirects | máx. 3, solo a `https`, nunca a otro host sin re-validar | n/a |
| Tamaño máximo | definido (OD-5) | idem |
| Timeout | connect + read separados | idem |
| Host permitido | lista explícita (p. ej. `codeload.github.com`) | derivado del host permitido |
| Verificación de contenido | **no hay mecanismo criptográfico actual** (ver §19) | idem |

`http://` se elimina del camino remoto. Un slug se traduce a un host de la
lista permitida, nunca a una URL arbitraria.

## 17. Seguridad de descargas

Controles obligatorios en el cliente de descarga remoto:

| Control | Regla |
| --- | --- |
| Validación de URL | esquema `https`; host en lista explícita; sin credenciales embebidas (`user:pass@`); sin fragmento |
| TLS | `ssl.create_default_context()` con verificación activa; sin `CERT_NONE`; sin seguir a `http` |
| Redirects | máximo 3; cada redirect re-validado contra esquema y host permitidos; un redirect a host no permitido aborta |
| Tamaño | streaming con contador; al superar `MAX_DOWNLOAD_BYTES` (OD-5) se aborta y se borra el parcial |
| Compresión | rejection de ratio de compresión anómalo (anti zip-bomb) durante la extracción |
| Timeout | `connect` y `read` separados, ambos acotados |
| Destino | `TMPDIR` dedicado, creado con `0o700`, fuera del workspace hasta la verificación |
| Retries | ninguno implícito en remoto; como máximo 1 con backoff fijo |
| User-Agent | fijo, sin datos del cliente |
| Proxies | solo si hay proxy declarado por el operador; nunca del entorno heredado |

Tras la descarga, el artefacto queda en estado **untrusted** hasta §19.

## 18. Extracción de archivos

Hoy `ZipFile.extractall(destino_tmp)` no aplica ninguna comprobación. La
extracción remota debe:

1. **Rechazar la entrada completa** si el archivo no es un zip simple
   (symlinks, hardlinks, device files, fifos, sockets) o si el ratio de
   compresión supera el umbral.
2. **Por cada entry**, antes de escribir:
   * rechazar nombres absolutos (`/etc/passwd`, `C:\…`);
   * rechazar cualquier componente `..`;
   * canonicalizar destino y comprobar containment con la **misma** primitiva
     de la frontera de B9.61-B (`Frontera.resolver_ruta`), no con
     `startswith`;
   * resolver symlinks del destino y re-verificar containment (symlink
     preexistente en el destino no puede redirigir la escritura);
   * rechazar entradas cuyo `realpath` caiga fuera del directorio de
     extracción.
3. **Rechazar duplicados** exactos y colisiones de nombre tras normalización
   (incluida normalización Unicode NFC y comparación case-insensitive en
   Windows) para impedir la sobrescritura de una entrada ya
   validada por otra.
4. **Recursión**: un zip dentro de un zip **no** se extrae automáticamente.
5. Aplicar un límite de número de entradas y de tamaño total descomprimido.
6. **Escribir sin seguir symlinks y sin ventana de carrera (C-R1-01)**: la
   escritura se hace con descriptores de directorio relativos (`dir_fd`) y
   `O_NOFOLLOW` en cada componente (`snapcontext._escribir_entry_segura`). Un
   symlink preexistente en el destino, o introducido entre la validación y la
   escritura, hace que la entry se **rechace**. No basta con `realpath()`
   seguido de una escritura por ruta: la validación y la apertura ocurren en la
   misma operación sobre el descriptor ya abierto. Los puntos 4-5 (límites de
   recursos) siguen **diferidos** (C-R1-03).

El resultado se extrae en un directorio **de cuarentena** y no se mueve a su
destino final hasta completar la verificación (§19).

## 19. Frontera download → verify → unpack → inspect → install

Estados de confianza explícitos:

```text
UNTRUSTED (bytes descargados)
   ↓ verificación de formato y tamaño
QUARANTINED (extraído en tmpdir con 0o700)
   ↓ inspección de manifest y contenido
STAGED (validado, aún no instalado)
   ↓ decisión de instalación
INSTALLED (copiado al destino)
   ↓ habilitación explícita
ENABLED (ejecutable por el host)
```

* Descargar **no** es instalar.
* El manifest se inspecciona **antes** de copiar nada.
* La copia al destino usa la frontera de filesystem (canonicalización +
  containment), como cualquier escritura del gateway.
* El contenido se instala **deshabilitado**; habilitar es un acto separado,
  explícito y auditado.

**Sobre verificación criptográfica**: hoy **no existe** ningún mecanismo
(pin de commit, checksum firmado, firma de release). Se documenta
explícitamente en lugar de inventarlo. Mientras no exista, el modelo de
seguridad de un plugin remoto es:

```text
"el cliente remoto puede instalar código arbitrario que se ejecutará en el host"
```

y por tanto la instalación remota de plugins **debe** quedar detrás de una
decisión explícita (§30, OD-6), no detrás de "está en la allowlist de binarios".

## 20. Manifest

Campos del manifest y su naturaleza:

| Campo | Naturaleza | Política |
| --- | --- | --- |
| `nombre` / `name` | descriptivo | validado (string no vacío, longitud máxima) |
| `version` | descriptivo | validado (formato) |
| `descripcion`, `autor` | descriptivo | acotado en tamaño |
| `habilitado` | **estado** | un plugin remoto nace deshabilitado |
| `herramientas` | **ejecutable** | declara capacidades; no las concede (ver abajo) |
| `dependencies` | **ejecutable** | `DENY` en remoto (ver §21) |
| `permisos` | **solicitado** | declarativo; requiere convergencia con capabilities |
| `entrypoint` | **ejecutable** | debe estar confinado al directorio del plugin |
| `comandos`, `red`, `filesystem` | declarativo hoy | si se implementan, pasan por allowlist |

Regla central:

> **Un manifest nunca concede permisos.** Los campos `permisos`, `herramientas`,
> `network` o `filesystem` son **solicitudes**. El motor decide si se conceden
> contra una política cerrada; un manifest no puede auto-concederse.

Si un manifest declara una capacidad o un permiso no contemplado por la
política, la instalación se rechaza (fail-closed), no se ignora en silencio.

## 21. `pip install` y dependencias

Ruta actual: `marketplace.instalar_dependencias` ejecuta
`[sys.executable, "-m", "pip", "install", "--user", dep]` con `dep` tomado del
manifest, sin validación.

| Pregunta | Respuesta actual | Política remota M1 |
| --- | --- | --- |
| ¿Quién lo invoca? | carga de plugins habilitados | **DENY** |
| ¿Qué args controla? | `dependencies` del manifest | — |
| ¿Desde dónde instala? | índice por defecto de PyPI | — |
| ¿Qué entorno modifica? | `--user` → site del usuario | — |
| ¿Ejecuta scripts? | sí (post-install) | — |
| ¿Accede a Internet? | sí | — |
| ¿Escribe fuera del workspace? | sí | — |
| ¿Puede tocar el env de SnapContext? | `--user` puede solaparse | — |

**Política: `REMOTE = DENY`.** Un plugin remoto no puede instalar dependencias.
La instalación de dependencias, si se mantiene, es una operación **local**
exclusiva, con confirmación humana, allowlist de paquetes y sin red arbitraria.

Además, el destino de instalación (`PLUGINS_DIR = CONFIG_DIR/"plugins"`,
bajo el home) queda **fuera** del workspace: debe pasar por la frontera de
filesystem o declararse como ubicación de confianza del servidor, gestionada
por el operador y no alcanzable desde el request.

## 22. Descubrimiento vs instalación vs ejecución

Son capacidades distintas:

```text
PLUGIN_LIST    → enumerar plugins instalados
PLUGIN_INSTALL → descargar + verificar + copiar + (deshabilitado)
PLUGIN_ENABLE  → permitir que el host lo ejecute
```

`USE_PLUGINS` actual cubre las tres implicitly y es `solo_loopback`. Se
recomienda separar (§23) para que instalar no implique ejecutar.

## 23. Modelo de capacidades

Las 9 capacidades de B9.61-A se conservan. B9.61-C **no necesita** nuevas
capacidades si `USE_PLUGINS` se subdivide por operación mediante el dispatcher
cerrado ya existente (`CAPABILITY_MAP`), pero la honestidad del modelo exige
reconocer que hoy una sola capability cubre instalar y ejecutar.

| Capability | Uso en remoto | Requisito adicional |
| --- | --- | --- |
| `EXECUTE_REMOTE` | ejecución de comandos | identidad cerrada, argv, cwd, env, red |
| `USE_PLUGINS` | listar/instalar/habilitar | solo loopback; separar sub-operaciones |
| `READ_WORKSPACE` | lectura | inalterado (B9.61-B) |
| `WRITE_WORKSPACE` | escritura | inalterado (B9.61-B) |
| `MANAGE_TASKS` | tasks | contexto congelado (§25) |
| resto | — | sin cambio |

No se agregan capabilities por comodidad. Si la implementación descubre que
instalar y ejecutar no pueden separarse con la capacidad actual, entonces sí
procede una capability nueva, con su entrada en `CAPABILIDADES` y su mapeo
explícito — y esa decisión se ratifica (OD-7).

En cualquier caso:

```text
USE_PLUGINS  ⇏  EXECUTE_REMOTE
EXECUTE_REMOTE  ⇏  USE_PLUGINS
```

## 24. Identidad y ownership

Toda operación remota conserva y propaga:

```text
identidad del request   (credencial que autorizó)
identidad de workspace  (raíz congelada)
identidad de capability (cuál se ejercitó)
```

* Un plugin o un comando remoto **no cambia** la identidad de seguridad: no
  puede elevar, reasignar ni presentar otra credencial.
* El `origin` de una descarga (host, esquema) se registra; un plugin instalado
  conserva la trazabilidad de su procedencia.
* Los artefactos descargados llevan metadato de origen (host, timestamp,
  identidad que los instaló) para auditoría.

## 25. Contexto congelado en background tasks

Cuando una operación remota crea una tarea, el contexto se congela en el
momento del request (B9.60 §10):

```text
TaskSecurityContext =
    workspace_root        (realpath congelado)
  + capabilities          (intersección congelada; nunca ampliación)
  + identity              (credencial creadora, no el secreto)
  + remote_policy_version (la allowlist vigente en ese instante)
  + command_policy
  + plugin_policy
  + exposure_policy       (modo de exposición detectado)
  + credential_generation (época de la credencial que autorizó)
```

Reglas:

* El worker **revalida** el contexto antes de cada acción remota.
* Si la política remota cambió (allowlist editada), la tarea usa la versión
  nueva solo si sigue autorizando; en caso contrario, `DENY`.
* El `cwd` derivado de la tarea se valida contra el root congelado, nunca contra
  el cwd del proceso.
* La tarea no hereda `os.environ` del servidor; usa el entorno mínimo (§13).
* Una tarea nunca persiste credenciales.

## 26. Rotación de credencial

Semántica requerida:

| Situación | Comportamiento |
| --- | --- |
| Credencial rotada, operación en curso | termina con el contexto congelado ya autorizado (no se corta a mitad), salvo que la política lo prohíba |
| Credencial rotada, tarea **pendiente** de empezar | la tarea se revalida contra la credencial **vigente**; si la credencial ya no autentica, `DENY` |
| Credencial rotada, tarea en cola larga | igual que "pendiente": revalidación antes de ejecutar |
| Nueva request con credencial antigua | 401 (B9.61-A) |

Consecuencia: una tarea no conserva privilegios **indefinidamente**; el worker
comprueba la vigencia en cada ejecución. Una tarea creada con una credencial y
ejecutada mucho después debe fallar si la rotación ya la invalidó.

La rotación cierra además los WebSockets activos (hook existente en B9.61-A);
un comando remoto ya encolado en un hilo se considera "en curso" y se documenta
como tal.

## 27. Threat model

| Asset | Capacidad del atacante | Ataque | Frontera | Mitigación |
| --- | --- | --- | --- | --- |
| Workspace | entrada remota autenticada | comando arbitrario | política de comando | allowlist cerrada + identidad verificada (REX-1) |
| Workspace | entrada remota | shell injection en argv | argv | `list[str]` + `shell=False` (REX-2) |
| Host FS | entrada remota | escape de path (`cd`, `..`, symlink) | filesystem | cwd validado + containment (REX-3) |
| Binarios del host | entrada remota | PATH hijacking | PATH | `PATH_REMOTO` + verificación de ruta resuelta |
| Secretos del proceso | comando remoto | fuga por env | env | entorno mínimo (REX-4) |
| Red | comando remoto | egress arbitrario | red | política por entrada; binarios de red `DENY` |
| Store de plugins | entrada remota | plugin malicioso | plugin | estados de confianza; install ≠ enable |
| Entorno Python | plugin remoto | ejecución de código | install | `pip` `DENY` (REX-7) |
| Servidor | archivo remoto | zip-slip / symlink entry | extracción | containment por entry (REX-6) |
| Store de plugins | archivo remoto | zip-bomb | descarga | tamaño y ratio acotados |
| Downloads | entrada remota | MITM / downgrade | TLS | `https` verificado, sin `http` |
| Tareas | entrada remota | escalada tras rotación | contexto | revalidación (REX-10) |
| Identidad | plugin/comando | impersonación | identidad | contexto no transferible (§24) |
| Manifest | plugin remoto | auto-conceder permisos | manifest | solicitudes, no concesiones (REX-5) |

## 28. Invariantes de seguridad

* **REX-1** — Un comando remoto nunca ejecuta un binario fuera de la allowlist
  remota; la coincidencia es por identidad verificada, no por basename.
* **REX-2** — Un comando remoto nunca usa un shell o intérprete para ampliar su
  semántica; no existe `shell=True` en el camino remoto.
* **REX-3** — Un comando remoto no puede escapar del workspace: `cwd` y todo
  argumento de tipo ruta se validan contra `Frontera.raiz_efectiva()`.
* **REX-4** — Un comando remoto no hereda el entorno del servidor; recibe un
  entorno mínimo construido explícitamente.
* **REX-5** — Un plugin remoto nunca obtiene permisos por declararlos en su
  manifest; el manifest solicita, la política concede.
* **REX-6** — Un artefacto remoto descargado no puede escribir fuera del
  directorio de destino: cada entry se canonicaliza y confine antes de
  escribirse.
* **REX-7** — Un plugin remoto no puede ejecutar `pip install` (ni gestor de
  paquetes) por defecto.
* **REX-8** — Una referencia remota no puede convertirse ambiguamente en una
  ruta local; la clase local/remoto es explícita y fail-closed.
* **REX-9** — La política remota es cerrada: allowlist vacía o corrupta deniega
  todo, sin fallback a la política local ni al sandbox.
* **REX-10** — Una operación remota pendiente revalida identidad y política
  antes de ejecutarse; la rotación no deja privilegios indefinidos.
* **REX-11** — La política remota es un subconjunto de la local: todo comando
  permitido en remoto está permitido en local.
* **REX-12** — La resolución del ejecutable ocurre antes de la autorización y
  se registra; la ruta resuelta se verifica (regular, ejecutable, sin symlink
  fuera de `PATH_REMOTO`).
* **REX-13** — `USE_PLUGINS` no implica `EXECUTE_REMOTE` ni viceversa.
* **REX-14** — Ninguna respuesta de error a un cliente remoto revela rutas
  absolutas del host, tokens ni configuración interna.

## 29. Criterios de aceptación para la implementación

B9.61-C (implementación) no debe comenzar hasta que la revisión confirme:

1. command identity is closed
2. PATH cannot hijack executable selection
3. shell/interpreter execution is denied
4. argv is structured (no `shell=True` en remoto)
5. remote allowlist is closed (vacía ⇒ deny all)
6. cwd is workspace-bound
7. environment is minimal (no inheritance)
8. filesystem remains confined
9. network policy is explicit
10. plugin local/remote identity is explicit
11. downloads are bounded (esquema, host, tamaño, timeout, redirects)
12. archive extraction is confined (por entry)
13. manifests cannot grant permissions
14. pip/package-manager execution is denied by default
15. plugin installation is separated from plugin execution
16. capabilities are explicit
17. task context is frozen and revalidated
18. credential rotation semantics are defined
19. C2 (`clasificar_comando`) y C3 (`escribir_archivo_seguro`) siguen intactos
20. el CLI local no cambia de comportamiento

## 30. Decisiones abiertas — RATIFICADAS en B9.61-C-R

> Todas resueltas. Ver `docs/B9.61-C-DECISIONES-RATIFICADAS.md`.
> Resumen: OD-1 `DENY ALL`; OD-6 instalación remota `DENY`;
> OD-8 extracción segura ahora, firma/supply-chain diferida.


### OD-1 — ¿Existe alguna allowlist remota no vacía en M1?

* **Pregunta**: ¿se autoriza algún comando remoto, o el gateway arranca con
  `DENY ALL` y la ejecución remota se habilita después?
* **Opciones**: (a) `DENY ALL` en M1; (b) allowlist mínima de solo lectura
  (`git status/diff/log/show/rev-parse`, `ls`, `cat`, `wc`, `grep`, `rg`).
* **Impacto de seguridad**: (a) elimina toda la superficie de ejecución remota;
  (b) conserva superficie de lectura de workspace y de fuga de información vía
  `cat`/`grep` de archivos sensibles que estén dentro del workspace.
* **Dirección recomendada**: (a) `DENY ALL` en M1, con la estructura de
  allowlist definida pero vacía por defecto, habilitando (b) solo tras revisar qué datos
  del workspace son aceptables por un cliente remoto.
* **Bloqueante**: sí.

### OD-2 — ¿Dónde vive la allowlist remota?

* **Opciones**: (a) clave `sandbox_allowlist_remota` en `config.json` (mutable
  por el operador); (b) archivo del workspace versionado; (c) embebida en el
  código, ampliada solo por config firmada.
* **Impacto**: (a) simplest, pero un config comprometido amplía la política;
  (b) revisable por PR, pero un workspace clonado podría manipular la
  política; (c) la más segura, peor operativa.
* **Dirección recomendada**: (a) como fuente, **más** validación estricta al
  cargar (fail-closed, sin herencia de la local) y advertencia explícita de que
  el config es superficie privilegiada.
* **Bloqueante**: sí.

### OD-3 — ¿Se permite algún intérprete en remoto?

* **Opciones**: (a) `DENY` absoluto; (b) intérprete con argv cerrado por
  subcomando y sandbox real.
* **Impacto**: (a) cierra el vector más amplio; (b) reintroduce ejecución de
  código y necesita aislamiento real que hoy no existe.
* **Dirección recomendada**: (a) `DENY` en M1.
* **Bloqueante**: no (ya decidido por §6; se ratifica).

### OD-4 — ¿Pytest remoto?

* **Opciones**: (a) `DENY`; (b) permitido solo con workspace de solo lectura y
  sandbox.
* **Impacto**: pytest ejecuta `conftest.py` y hooks ⇒ ejecución de código del
  proyecto.
* **Dirección recomendada**: (a) `DENY`.
* **Bloqueante**: no.

### OD-5 — Límites de descarga

* **Pregunta**: tamaño máximo de archivo, timeout y ratio de compresión.
* **Opciones**: valores únicos por defecto vs. configurables por entrada.
* **Impacto**: límites bajos bloquean plugins legítimos; límites altos abren
  DoS (zip-bomb, disco lleno).
* **Dirección recomendada**: valores por defecto conservadores y
  configurables, con la tasa de compresión acotada como ratio (p. ej. 100:1)
  además del tamaño total.
* **Bloqueante**: no (parámetro, no arquitectura).

### OD-6 — ¿Instalación remota de plugins?

* **Contexto**: no hay verificación criptográfica (§19); instalar un plugin
  remoto implica ejecutar código en el host.
* **Opciones**: (a) prohibir `plugin_install` remoto; (b) permitir solo con
  allowlist de hosts y plugin instalado deshabilitado; (c) permitir con
  verificación de firma obligatoria (requiere infraestructura previa).
* **Impacto**: (a) elimina la superficie; (b) deja el riesgo en el
  operador; (c) es la solución correcta pero no es implementable todavía.
* **Dirección recomendada**: (a) para M1; (b) solo si el producto lo requiere y
  con confirmación explícita; (c) es la dirección final.
* **Bloqueante**: sí.

### OD-7 — ¿Capacidades nuevas?

* **Opciones**: (a) mantener `USE_PLUGINS` y separar sub-operaciones en el
  dispatcher; (b) añadir `PLUGIN_INSTALL` / `PLUGIN_ENABLE`.
* **Impacto**: (a) menos superficie en el mapa; (b) modelo más honesto pero
  amplía el conjunto cerrado de B9.61-A.
* **Dirección recomendada**: (a) para M1, con separación explícita en
  `CAPABILITY_MAP`; (b) si la auditoría revela que no es separable.
* **Bloqueante**: no.

### OD-8 — Aislamiento de red

* **Opciones**: (a) sin red para comandos remotos por defecto, `DENY` de
  binarios de red; (b) namespace de red o egress filtering real.
* **Impacto**: (a) depende de la disciplina de la allowlist; (b) requiere
  privilegios o de runtime, no disponible hoy.
* **Dirección recomendada**: (a) para M1, documentando la limitación; (b) como
  objetivo.
* **Bloqueante**: no.

### OD-9 — Destino de instalación de plugins

* **Contexto**: `PLUGINS_DIR` está bajo el home, fuera del workspace.
* **Opciones**: (a) moverlo dentro del workspace; (b) declararlo ubicación de
  confianza del servidor, no alcanzable desde el request; (c) ruta configurable
  validada al arrancar.
* **Impacto**: (a) acopla el store al workspace (multiples workspaces, backup);
  (b) coherente con el modelo; (c) flexible con validación.
* **Dirección recomendada**: (c), con validación de raíz al arranque y
  prohibición de que el request lo elija.
* **Bloqueante**: no.

### OD-10 — Verificación criptográfica de plugins

* **Pregunta**: ¿se diseña ahora el formato de firma/pin aunque la
  implementación se difiera?
* **Opciones**: (a) especificar el formato ahora; (b) diferir y mantener
  `DENY` remoto mientras no exista.
* **Impacto**: sin verificación, el modelo de riesgo de plugins remotos es
  "ejecución arbitraria confiada al operador".
* **Dirección recomendada**: (b) para M1, con (a) como requisito de la
  habilitación futura.
* **Bloqueante**: no.
